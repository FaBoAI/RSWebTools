# アダプタが生きているか切り分ける

「シリアルポートは見えているのにモータが見つからない (RX が 0 のまま)」ときに、
**USB-CAN モジュールの MCU が動いているか**を判定する手順です。

## DIP スイッチの正しい設定

RobStride 純正 USB-CAN モジュールには DIP スイッチが 2 個あります。

| スイッチ | 正しい設定 | ON にすると |
|---|---|---|
| **1** | **OFF** | Boot モードに入り、**ホストと一切通信できない** |
| **2** | **ON** | 120Ω 終端抵抗が接続され、正常に通信できる |

つまり **1 = OFF、2 = ON** が通常の運用設定です。

### なぜ「ポートは見えるのに無応答」になるのか

```
[PC] --USB--> [CH340 USB-シリアル変換] --UART--> [GD32 MCU] --CAN--> [モータ]
                      ↑                              ↑
              ここは常に enumerate される      DIP1=ON だとここが Boot で沈黙
```

CH340 は MCU より手前にあるため、DIP 1 が ON でも `/dev/cu.usbserial-*` は
正常に現れます。しかし MCU がブートローダで止まっているので、UART には
何も出てきません。

## 総当たりプローブ

```bash
./.venv/bin/python tools/probe_adapter.py /dev/cu.usbserial-XXX
```

シリアル速度 9 種 (9600〜2000000) × コマンド 11 種 (`AT`, `AT+AT`, `AT+VER`,
slcan の `V\r` など) を送り、1 バイトでも返ってくるかを確認します。

| 結果 | 判定 |
|---|---|
| 何かしら応答がある | MCU は生きている。CAN 側 (電源・結線・ボーレート) を疑う |
| **全通り無応答** | MCU が動いていない → 下記の 3 つを疑う |

全通り無応答だった場合:

1. **DIP スイッチ 1 が ON になっている** (最も多い)
2. モジュールの故障・電源不良
3. そもそも RobStride USB-CAN モジュールではなく、**素の CH340 USB-TTL 変換基板**
   を挿している (VID:PID はどちらも `1A86:7523` で見分けがつかない)

## CAN 側の切り分け

MCU が生きていることが確認できたら、次は CAN バス側です。
アプリの「CAN コンソール」タブで TX / RX を見ながら:

- TX 行だけ並ぶ → フレームは出ている。モータ電源 / CAN H・L / ボーレート / CAN_ID を確認
- TX も出ない → シリアル書き込みが失敗している。ポートを他プロセスが掴んでいないか確認

> 本アプリのサーバはシリアルポートを占有します。公式 Python SDK など別のツールで
> 試すときは、先に UI で **切断** してください。

## CAN 側の総当たり診断

```bash
# 3 プロトコル (私有 / MIT / CANopen) × ID 0-127 を読み出しのみで総当たり
./.venv/bin/python tools/probe_bus.py /dev/cu.usbserial-XXX

# 電源投入時のフレームを捕まえる (実行後にモータの電源を入れ直す)
./.venv/bin/python tools/probe_bus.py /dev/cu.usbserial-XXX --listen 30
```

`--listen` が重要な理由: モータはバスに復帰したとき通信タイプ 0 のフレームを自発送信します
(公式 Python SDK のコメントに記載)。CANopen に切り替わっている場合は起動時に
`0x700 + node_id` のブートアップメッセージを出します。**どちらか一つでも捕まえられれば
CAN リンクは生きている**と断定でき、以降は ID とプロトコルの問題に絞れます。

## TX LED が点滅していても安心できない

多くの CH340 基板では TX/RX の LED が **CH340 のデータ線に直結**されています。
この場合 LED は「PC から USB-シリアル変換までは届いた」ことしか示さず、
その先の MCU が動いているか、CAN に流れたかは分かりません。

LED だけでは MCU の生死は確定しないため、上の `--listen` テストで
**バス上に何か流れてくるか**を見るのが確実です。

## テスターでの確認 (最も確実)

**すべての電源を切った状態**で、CAN H と CAN L の間の抵抗を測ります。

| 実測値 | 判定 |
|---|---|
| **約 60Ω** | 正常。両端に 120Ω 終端がある |
| 約 120Ω | 終端が片側だけ。1Mbps では通信できないことがある |
| ∞ (導通なし) | **結線が繋がっていない**。コネクタのピンアサインを確認 |
| 数Ω 以下 | CAN H と L が短絡 |

あわせて確認すること:

- モータ側コネクタで**電源電圧が実際に出ているか** (24V / 48V など機種の指定値)
- モータ本体の LED が正常な状態を示しているか
- CAN H / CAN L が逆になっていないか

## 実測メモ: macOS 標準 CH340 ドライバはこのアダプタで使えない

**症状**: ポートは `/dev/cu.usbserial-*` として正常に見えるのに、モータが一切応答しない。
モータの電源投入時だけ 17 バイトのバイト列が届くが、内容が化けている。

**原因**: macOS 標準の CH340 ドライバ `com.apple.DriverKit-AppleUSBCHCOM` が
921600bps でデータを壊していた。

**対策**: WCH 公式ドライバ (CH34xVCPDriver) に入れ替える。

1. 公式リポジトリから入手する
   <https://github.com/WCHSoftGroup/ch34xser_macos>
   (ミラー: <https://www.wch.cn/downloads/CH34XSER_MAC_ZIP.html>)

2. `CH34xVCPDriver.dmg` を開き、`CH34xVCPDriver.app` を `アプリケーション` へ
   ドラッグしてから、アプリを起動して **Install** を押す

3. `システム設定` → `一般` → `ログイン項目と機能拡張` → `ドライバ機能拡張` で
   **CH34xVCPDriver** を有効にする
   (macOS のバージョンによっては `プライバシーとセキュリティ` に
   「"CH34xVCPDriver" の機能拡張がブロックされました」と出るので **許可** を押す)

4. **アダプタを挿し直す**

   ドライバを入れたときにアダプタが挿さったままだと、デバイスの再マッチングが
   起きず標準ドライバが掴んだままになる。実際にこれで詰まったので必ず抜き挿しする。

成功するとポート名が `/dev/cu.wchusbserial*` に変わる。

```bash
ls /dev/cu.wchusbserial*                      # ポート名で判別
ioreg -p IOService -l -w0 | grep -i CHCOM     # 標準ドライバが残っていないか
systemextensionsctl list | grep -i wch        # 有効化されているか
```

`systemextensionsctl list` に `[activated enabled]` と出ているのにポート名が
`cu.usbserial-*` のままなら、**手順 4 (挿し直し) をしていない**状態です。

### 標準ドライバのときに何が起きていたか

921600bps で受信したバイト列 (モータ電源投入時):

```
A1 A4 80 83 FF F8 80 A9 A6 9B CA 80 B4 98 89 85 82
```

17 バイト全部が 0x80 以上で、フレーム末尾の CRLF すら出てきません。
受信速度を上げると構造だけは合ってきますが (1,000,000 で末尾 `0D 0A` と
DLC `08` が正位置に出る)、先頭 2 バイトの上位ビットがフレームごとに
ランダムに化け続け、最後まで正常なフレームにはなりませんでした。

**この「速度を上げると構造が合う」現象に引きずられて、一時
「モジュールの真の速度は 1,000,000 では」と誤った推定をしました。**
実際にはドライバがビットを壊していただけで、**正しい速度はマニュアルどおり
921600bps** です。WCH ドライバに替えた直後、921600 で一発で通信できました。

同じ症状に遭ったら、ボーレートを疑う前にまずドライバを確認してください。
判別材料は以下です。

| 観測 | 示唆 |
|---|---|
| ポート名が `cu.usbserial-*` | macOS 標準ドライバ。**まずこれを疑う** |
| ポート名が `cu.wchusbserial*` | WCH 純正ドライバ。速度側を疑ってよい |
| 速度を変えると「構造だけ」合う点がある | ドライバによるビット破壊の可能性 |
